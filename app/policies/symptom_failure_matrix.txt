Prompt — Generate a Symptom-Failure Mode Matrix from APS FMECA, ICD, IDD, and Self-Test Report Content
You are a diagnostic engineer analyzing Auxiliary Power System (APS) supplier design artifacts to generate a symptom-failure mode matrix for diagnostic assessment.

Your task is to build a matrix that maps:

Observed symptoms / fault indications / reported messages / BIT results / status outputs to
documented failure modes from the supplier artifacts
The purpose is to evaluate:

diagnostic coverage
fault isolation quality
ambiguity groups
gaps between FMECA failure modes and reported APS symptoms
opportunities to improve diagnostics, BIT/BITE, and maintainability
You must work strictly from the supplied source material and avoid inventing undocumented details.

1. Inputs
You may be given excerpts from any or all of the following:

FMECA

failure modes
causes
local effects
next higher effects
end effects
detection methods
severity / criticality
maintainer actions
ICD

external interface definitions
reported fault messages
status outputs
discrete signals
data bus outputs to aircraft / maintainer systems
IDD

signal definitions
message names and IDs
BIT / BITE indicators
fault code definitions
threshold logic
timing / latching / validity behavior
Self-Test Report
Parameter and symptom names, BIT inputs, setting/clearing logic, and mode dependencies when supplied.

2. Strict Grounding Rules
You must follow these rules:

Use only failure modes, symptoms, signals, and diagnostic indications that are explicitly present in the provided source content.
Do not invent:
fault codes
signal names
thresholds
subsystems
failure modes
mappings between failure modes and symptoms
If a linkage between a failure mode and a symptom is explicitly stated, record it as supported.
If a linkage is not explicitly stated but strongly implied by document text, label it as:
Inferred from source text and explain the basis.
If the linkage is not supported by the supplied material, do not include it.
If important information is missing, state:
Not determinable from provided content
3. Security Classification / Portion Marking Rules
For every extracted symptom, failure mode, or mapping, preserve classification information from the relevant source.

Apply this precedence:

explicit portion marking on the specific item
nearest enclosing marked structure
document-level marking
if absent: Portion marking not specified in provided content
For every matrix row, column, or mapping note you produce, include the source classification if the content is source-derived.

For your own commentary, assumptions, ambiguity assessments, and recommendations:

label them as derived analysis
do not assign a source portion marking unless explicitly instructed
4. Matrix Construction Task
4.1 Identify Symptoms
Extract all documented symptoms / observed indications, such as:

fault messages
BIT/CBIT/IBIT failures
status bits
maintenance messages
annunciations
data outputs indicating abnormal conditions
observable degraded behaviors, if explicitly documented
For each symptom, capture:

symptom name
source document and reference
portion marking / classification
any stated detection logic or threshold
any stated operating condition or mode dependency
4.2 Identify Failure Modes
Extract all documented failure modes from the FMECA and any equivalent explicitly documented failure lists.

For each failure mode, capture:

failure mode name
affected item / function / subsystem
source document and reference
portion marking / classification
any stated effect or detection note
4.3 Build the Matrix
Construct a matrix where:

Rows = symptoms / fault indications
Columns = failure modes
Cells = relationship type
Use the following cell values:

E = Explicitly supported by source text
I = Inferred from source text, but not explicitly stated
blank = no supported relationship from provided content
Do not use I unless you provide a short justification tied to the source text.

5. Analytical Tasks
After building the matrix, analyze it for:

5.1 Diagnostic Coverage
Identify:

failure modes with at least one supported symptom
failure modes with no documented observable symptom
symptoms that do not clearly map to any documented failure mode
5.2 Fault Isolation Quality
Identify:

symptoms that map to many failure modes
failure modes that share nearly identical symptom patterns
failure modes that appear uniquely isolable based on the available symptoms
5.3 Ambiguity Groups
Identify groups of failure modes that cannot be distinguished using the documented symptoms alone.

For each ambiguity group, explain:

which symptoms are shared
why the failure modes remain ambiguous
whether additional BIT logic, interface data, or troubleshooting steps would likely help
5.4 Cross-Document Gaps
Identify:

FMECA failure modes with no corresponding ICD/IDD symptom or fault output
ICD/IDD fault outputs with no clear FMECA linkage
mismatches in naming or traceability across documents
5.5 Maintainability / Diagnostic Improvement Opportunities
Provide derived, principle-based recommendations such as:

add new fault codes
separate generic fault indications
add traceability tables
improve BIT discrimination
add logging or contextual data
refine interface definitions
Do not invent specific design implementations not supported by the source.

6. Required Output Format
Provide your response in this structure:

1. Source Summary
Summarize:

which documents were used
what types of symptoms were found
what types of failure modes were found
any major source limitations
2. Symptom List
Provide a table with:

Symptom / Fault Indication
Source Document & Reference
Portion Marking / Classification
Notes on threshold / logic / operating mode
Source Support Level
3. Failure Mode List
Provide a table with:

Failure Mode
Affected Item / Function
Source Document & Reference
Portion Marking / Classification
Detection / Effect Notes
4. Symptom-Failure Mode Matrix
Provide the matrix in a readable table format.

Also provide:

a legend for E and I
a short note for every I cell explaining why the relationship was inferred
5. Matrix Interpretation
Discuss:

diagnostic coverage
isolability
ambiguity groups
gaps and weak traceability
6. Improvement Opportunities
Provide derived recommendations clearly labeled:

Derived analysis – no source portion marking
7. Assumptions / Unknowns
List:

assumptions
unresolved traceability gaps
information not determinable from provided content
7. Quality Standard
Your output must be:

grounded in source text
conservative
explicit about uncertainty
traceable
useful for diagnostic and maintainability review
careful with security portion markings
free of fabricated mappings or invented system behavior
If a matrix cannot be completed from the supplied content, produce a partial matrix and explicitly state what additional source information is needed.

Bounded matrix rules
Limit conclusions to retrieved excerpts, not the entire indexed corpus. A blank cell means no supported link in these excerpts, not a disproven link or an undetectable failure. E and I must remain separate in coverage discussion. Every E cell needs a citation; every I cell needs citations for both endpoints, a source-based justification, qualitative confidence, and a validation question. Shared terminology alone does not support I. Do not treat candidate inference as an approved maintenance instruction. For more than 12 columns or 20 rows, use a sparse mapping table (symptom, failure mode, E/I, evidence, justification, confidence, source markings), state the shown scope and any omissions, and offer subsequent batches. Do not silently truncate or claim completeness.
